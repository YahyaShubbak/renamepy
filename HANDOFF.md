## 1. Operational Protocol (For Active & Successor Agents)
1. **Strict Single-Item Execution:** Process items in exact sequential order. Never work on more than ONE item per turn.
2. **State Tracking:** Before editing code, set the item status to `[IN_PROGRESS]`.
3. **Surgical Precision:** Implement only the specified fix. Avoid drive-by refactorings. Rely on **Code Anchors** (function signatures / unique lines) rather than raw line numbers, as prior edits shift line numbers.
4. **Verification:** Run existing tests, type-checkers, or linters affecting the modified module before declaring completion.
5. **Update Handoff:** Upon verification, mark the checkbox `[x]`, set status to `[DONE]`, and fill out the `Resolution & Diff Summary` (including any line/signature shifts that affect downstream tasks).
6. **Commit & Halt:** Output a copy-pasteable Conventional Commit message in the chat, then **STOP COMPLETELY** and wait for explicit user confirmation before touching the next item.

## 2. System Context & Core Invariants
- **Architecture & Data Flow:**
  - Entry: `RenameFiles.py` → `modules/main_application.py::main` → `FileRenamerApp` (QMainWindow). State lives in `state_model.RenamerState` (`files`, `original_filenames {current_path: original_basename}`, `timestamp_backup {path: {atime, mtime, ctime, windows_creation_time}}`, `exif_backup {path: {tag: value}}`, `selected_metadata`).   - Rename: `rename_files_action` → `RenameWorkerThread(mode="plan")` → `RenamePlanner.build_plan()` (group RAW/JPG by dir+stem → batched metadata read → sort by capture time → per-date or continuous counter → `filename_components.build_named_components` / `compose_filename` → `file_utilities.get_safe_target_path` + in-memory `reserved_targets` → optional sidecar entries) → `plan_ready` → `dialogs/rename_plan_dialog.py` → `RenameWorkerThread(mode="execute")` → `_sync_then_execute`: optional `exif_processor.batch_sync_exif_dates` (EXIF date → file times) → `execute_plan` (journal → `file_utilities.safe_rename` loop → journal settle/rekey → optional `exif_undo_manager.batch_write_original_filenames`) → `finished` → `on_rename_finished` (merge backups, rekey by new path, rebuild list). All ExifTool **writes** are one-shot subprocesses fed by a UTF-8 argfile (`-@`).

  - EXIF time shift: `dialogs/exif_time_shift_dialog.py::TimeShiftWorker` — per chunk of 50: read → journal backup → `exiftool -AllDates±=` → re-read → verify per file.

### [x] ID-03: 🟠 Undo journal: write failures are swallowed, no fsync, a corrupt journal is silently overwritten
- **Status:** `[DONE]`
- **Location:** `modules/backup_journal.py`; callers in `modules/rename_engine.py`, `modules/dialogs/exif_time_shift_dialog.py`
- **Code Anchor:** `def _write_journal_unlocked(data)` (Approx. Lines: `125–142`), `def _read_journal_unlocked()` (`106–122`), `def save_backup`, `def update_entries`, `def rekey_journal`, `def record_originals(self, values)` (`296–310`); `backup_journal.update_entries({"original_filenames": {"set": ...}})` at the top of `execute_plan`; `created = exif_backup.record_originals(new_backups)` in `TimeShiftWorker.run`
- **Root Cause & Impact:** `_write_journal_unlocked` catches `OSError`, logs, and returns nothing. `record_originals` therefore reports the keys as recorded and the destructive write proceeds with a memory-only backup (reproduced: unwritable app-data path → `record_originals` returned `{'x'}`, journal on disk `{}`). The module's stated contract ("durable before the destructive write") fails silently; a crash or normal close then loses the only copy of the original timestamps / EXIF dates. The tmp file is not fsynced before `os.replace`, so a power loss can leave an empty journal. A journal that fails to parse is treated as `{}` and the next write replaces it, destroying whatever was recoverable.
- **Implementation Blueprint:**
  1. `_write_journal_unlocked` returns `bool`; before `os.replace` add `f.flush(); os.fsync(f.fileno())` inside the `with`.
  2. `save_backup`, `clear_backup`, `update_entries`, `rekey_journal` return that bool (`True` when nothing had to be written).
  3. `_read_journal_unlocked`: on `JSONDecodeError`/`ValueError` or a non-dict payload, best-effort `os.replace(path, f"{path}.corrupt-{int(time.time())}")`, log at error level, return `{}`. Leave the plain `OSError` branch as is.
  4. `PersistedBackupDict.record_originals`: if `save_backup(...)` returns False, remove the `new` keys again (`dict.pop` via `super()`) and return `set()`.
  5. Callers: `batch_sync_exif_dates` needs no change (its existing guard `file_path not in backup_data and os.path.exists(file_path)` → "Could not back up the original timestamps - skipped" now triggers). `TimeShiftWorker.run`: for `set(new_backups) - created` append `(path, "Could not save the undo backup - skipped")` and drop those paths from `eligible`. `execute_plan`: if the pre-loop `update_entries` returns False, append `("", "Could not write the undo journal - no files were renamed")` and return before the loop.
  6. `__setitem__`/`update`/`pop` stay unchanged (not used on destructive paths; `sync_exif_date_to_file_date` is always called with `backup_timestamps=None` by `batch_sync_exif_dates`).
- **Verification Criteria:** New tests in `Tests/test_data_integrity.py`: (a) `monkeypatch.setattr(backup_journal, "get_app_data_dir", lambda: <path of a regular file>)` → `record_originals` returns `set()` and the dict is unchanged; `batch_sync_exif_dates` leaves the file's mtime untouched and reports the skip error; `execute_plan` renames nothing. (b) Write garbage into `pending_undo.json`, call `load_journal()` then `save_backup(...)` → a `pending_undo.json.corrupt-*` file exists with the garbage. Run `python -m pytest Tests/test_data_integrity.py Tests/test_rename_plan.py -q`.

### [x] ID-04: 🟠 Time shift drops a file's backup when the result cannot be verified; zero shift rewrites every file
- **Status:** `[DONE]`
- **Location:** `modules/dialogs/exif_time_shift_dialog.py`
- **Code Anchor:** `exif_backup.remove_many(f for f in failed if f in created)` in `TimeShiftWorker.run` (Approx. Lines: `127–136`); `def _dates_shifted(before, after, delta)` (`142–151`); `def apply_time_shift(self)` (`379`)
- **Root Cause & Impact:** A file counts as failed when no backed-up field moved by exactly `delta` — which is also the case when the *after* read returned `{}` (file locked, share hiccup, ExifTool killed by the timeout) or when dates moved by a different amount. The backup created for that file is then removed although the file may have been modified: undo is impossible and the user, told "Dates were not changed", shifts again (double shift). Separately the dialog allows 0 h 0 min: `-AllDates+=0:00:00` rewrites every file and every file "verifies".
- **Implementation Blueprint:**
  1. Add `_dates_unchanged(before, after)`: True iff `after` is non-empty and every `BACKUP_DATE_FIELDS` entry present in `before` has an equal value in `after`.
  2. In the per-file loop after the shift classify: shifted → success; `after` empty → error "Could not verify the result - backup kept, check the file before shifting again" (keep backup); `_dates_unchanged` → error as today and drop the backup if created in this run; anything else → error "Dates changed unexpectedly - backup kept" (keep backup).
  3. Change the `remove_many` argument to only the "verifiably unchanged" files that are in `created`.
  4. In `apply_time_shift`, return early with an information box when `hours == 0 and minutes == 0`.
- **Verification Criteria:** Tests next to the existing `TimeShiftWorker` tests in `Tests/test_data_integrity.py` (~lines 300–350, they patch `get_exiftool_metadata_batch` and call `worker.run()`): after-read returns `{}` → the path is still in the journal's `exif_backup` and an error is reported; after-read equals before-read → backup removed. `python -m pytest Tests/test_data_integrity.py Tests/test_exiftool_integration.py -q`.
- **Resolution & Diff Summary:** Implemented as specified.
  - New module function `_dates_unchanged(before, after)` (~168, after `_dates_shifted` ~156): False for an empty `after`, else every `BACKUP_DATE_FIELDS` key of `before` has the identical raw value in `after`.
